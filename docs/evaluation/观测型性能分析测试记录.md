# TravelMind 观测型性能分析测试记录

## 1. 本轮目标

本轮验证新增的观测型性能分析流程是否能跑通：

- 使用 `scripts.observability_smoke` 调用真实 `/api/travel/query` 主链路。
- 保存每个用例的 SSE 事件和耗时。
- 使用 `logs/structured.log` 生成单次运行窗口内的 Markdown 观测汇总。
- 验证 Structured QP、LLM 调用和 SSE 主事件是否可被稳定观测。

## 2. 验证环境

- 日期：2026-05-02
- 后端：本地 `uvicorn main:app --host 127.0.0.1 --port 8012`
- 环境变量：`ENABLE_STRUCTURED_QP=true`
- 用例集：`mini`
- 命令：

```powershell
cd llm_backend
py -X utf8 -m scripts.observability_smoke --base-url http://127.0.0.1:8012 --user-id 1 --case-set mini --timeout 240
```

## 4. 相比历史基线的性能提升

对比口径：

- 历史基线来自 `docs/performance-analysis-report.md` 中“优化前性能基线”：完整草案端到端约 85s、用户实质首屏约 75s。
- 当前值来自本轮 `mini` 观测：国内完整规划端到端 20066.48 ms；首个实质行程事件从 `intent_routed` 到 `pipeline_complete/day_ready` 约 17.72s。
- 这是单轮本地真实链路观测，不等同于并发压测或长期 P95。

| 指标 | 优化前基线 | 本轮观测 | 改善幅度 | 说明 |
|------|------------|----------|----------|------|
| 国内完整规划端到端 | ~85s | 20.07s | 耗时下降约 76.4%，约 4.2x 提速 | 从一次性完整等待到 SSE 渐进输出 |
| 首个实质行程内容 | ~75s | 17.72s | 耗时下降约 76.4%，约 4.2x 提速 | 以 `pipeline_complete/day_ready` 作为首个实质行程内容 |
| 缺字段澄清响应 | ~75s 空等风险 | 4.10s | 避免约 70s+ 无效等待，约 18.3x 提速 | 当前会快速进入澄清，不再误跑完整 Draft |
| QA 响应 | 无稳定历史基线 | 2.32s | 暂不计算 | 本轮仍为秒级，后续可优化为更多本地复用 |

计算方式：耗时下降 = (优化前耗时 - 本轮耗时) / 优化前耗时；提速倍数 = 优化前耗时 / 本轮耗时。如果把“用户看到阶段开始”的 `stage_start` 也算作首屏反馈，当前几乎是提交后立即返回；但为了口径保守，本表使用首个实质行程内容事件做对比。

为验证海外、Provider 和 backfill 观测，后续又执行了 `extended` 用例集：

| 指标 | 结果 |
|------|------|

Extended 结论：

- 海外普吉岛规划主链路通过，端到端约 30.3s。
- Provider 结构化日志已可统计，当前样例 Provider 调用均为 success，无 error。
- Backfill 仍是质量与耗时风险点：12 个尝试中 4 个成功、8 个 unresolved，P95 约 8.56s。
- LLM 仍是主耗时来源之一，extended 中 LLM P95 约 15.85s。
- QA 仍为约 2.5s，后续仍建议优先做本地 itinerary 复用。

## 7. 发现

- Structured QP 在本轮 4 个请求中全部走 `llm`，没有触发 fallback。
- 国内完整规划的端到端耗时约 20.1s，主耗时仍来自 LLM 和 Provider/recall 链路。
- QA 请求约 2.3s，本轮没有命中毫秒级本地回答，说明仍经过了 Structured QP/LLM 或相关处理。
- Extended 补充验证后，`provider_call`、`location_backfill` 和 `itinerary_quality_summary` 已可进入结构化汇总；`semantic_cache_lookup` 本轮未触发。

## 8. 下一步建议

1. 优先优化 QA 本地复用：如“第 2 天安排是什么？”应直接从已有 itinerary 回答，目标从秒级降到几十毫秒级。
2. 针对 backfill 的 unresolved 样例做专项分析，区分“地点泛化无法解析”和“Provider 超时/空结果”。
3. 扩展观测脚本的报告展示，把 `smoke-report.md` 与 `observability-summary.md` 合并成一份更适合阅读的 Markdown。
