## 一、简历描述

### 推荐版（一段式，直接粘贴）

**TravelMind — 面向旅行规划 Agent 的 POI 候选排序与质量优化系统**

从零设计并实现的旅行规划 Agent，将高德、SerpAPI、Mock 等工具返回的 POI 结果抽象为候选集，围绕目的地 bbox、文本匹配、alias、provider 状态、evidence coverage、预算和行程约束进行候选排序、过滤、回填诊断和 badcase 迭代；项目不定位为传统 CTR/CVR 推荐系统，而是面向 Agent 岗位中的 Tool/Provider Result Ranking 与候选决策质量优化。

核心工作包括：(1) 设计 4 节点 LangGraph 工作流（约束提取→并行检索→流式 LLM 生成→后处理），通过条件边实现缺字段早退（<2ms）和正常流程的智能路由；(2) 构建 QP→Provider 召回→POI 候选排序→约束过滤→Evidence Builder 的候选决策流水线；(3) 从 `location_backfill` 结构化日志中导出 `candidate_decision_v1` 数据集，记录 accepted/rejected/skipped、bbox_rejected、provider_timeout、negative_cache、quality_breakdown 等诊断，并自动生成 badcase report 与 run-level manifest；(4) Provider 层抽象高德/SerpAPI/Mock 多数据源，支持 timeout、quota switch、SerpAPI response cache 和 degraded fallback；(5) 设计 itinerary v1 结构化行程契约，支持 revision/diff、Edit Day/slot patch 与编辑后局部坐标/evidence 回填。

技术栈：Vue 3 + TypeScript、FastAPI、LangGraph、DeepSeek LLM、Redis、MySQL

### Bullet 版（可直接写入简历）

**TravelMind：POI 候选排序增强的旅行规划 Agent（毕业设计）**　　　　　　　　　　　　　　　2025年12月 - 2026年03月  
**技术栈：** Python、FastAPI、LangGraph、Pydantic、MySQL（SQLAlchemy）、Redis、Vue3、TypeScript、JWT、SSE、高德/SerpAPI

- **目标与定位：** 从零设计并实现旅行规划 Agent，主线聚焦 Agent 场景下的 POI 候选排序与工具结果选择；系统将高德/SerpAPI/Mock 返回结果抽象为候选集，基于目的地 bbox、文本匹配、alias、provider 状态、evidence coverage 与预算/行程约束进行 rerank/filter，避免把 LLM 直接生成结果作为唯一决策来源。
- **意图识别与澄清：** 设计规则 QP baseline + Structured QP 模型增强，识别目的地、天数、预算等 P0 门槛字段；模型路径通过 feature flag 默认关闭，并用 Pydantic schema、置信度阈值、fallback_reason 和规则回退保证可控；信息缺失时先追问再生成，缺字段路径通过 LangGraph 条件边毫秒级返回，避免无效检索和大模型调用。
- **多轮会话状态：** 基于 conversation_id 维护对话上下文，并用 MySQL（SQLAlchemy）持久化当前行程、revision 和会话状态；构建 48 组、144 turn 的自然语言回放门禁，真实经过规则 QP、会话决策、澄清和状态迁移，覆盖目的地切换、城市提及只读、QA 零修改、连续局部编辑、reset 恢复和灵活回答，六项状态安全计数均为零。
- **端到端双语体验：** 设计相互独立的 UI locale 与会话级 `response_language`，将显式语言切换、当前输入、持久化状态与 UI locale 按优先级统一决策，并贯穿 create/clarify/QA/edit/reset/fallback 与 SSE 元数据；前端基于 `vue-i18n` 实现 English-first UI、EN/中文持久化切换和 locale 数字格式，20 组、42 turn 双语回放 `20/20` 通过，并通过桌面/390px 移动端双语浏览器验收。
- **候选排序流水线：** 落地「QP → Provider 召回 → POI 候选排序 → 规则过滤 → Evidence Builder」流水线，高德/SerpAPI 并行召回 POI 与地图候选，并按 bbox 地理一致性、文本匹配、alias、provider 状态、预算、评分、偏好和约束冲突等维度筛选；测试样例中检索阶段耗时由约 12s 降至约 3s，降低约 75%。
- **轻量学习排序：** 在 deterministic hard gate 后实现 NumPy pairwise linear ranker，基于偏好匹配、证据质量、Provider 置信度、可解析性、距离、预算、alias、评分和评论量等 9 维特征重排；构建 576 条分级样本、48 个请求、12 个目的地的可复现 rubric 数据集，并按目的地 ID 进行 8/2/2 训练、验证和测试隔离；门禁绑定 catalog、dataset 与模型训练指纹，避免陈旧产物和数据泄漏。离线 rubric benchmark 上 NDCG@5 从 0.694 提升至 1.0、推理 P95 低于 1ms；该结果只证明工程链路与人工偏好策略可学习，不宣称真实城市泛化或线上用户收益。模型默认关闭，支持 shadow/active 和异常回退。
- **候选数据闭环：** 构建 `candidate_decision_v1` 数据管道，从 `location_backfill` 结构化日志中导出 accepted/rejected/skipped 样本，记录 `risk_flags`、`quality_breakdown`、`provider_status_counts`、`variants_tried` 等字段，并自动生成 badcase report 与 run-level manifest，用于定位 `bbox_rejected`、`score_rejected`、`provider_timeout`、`cache_negative_hit` 等候选排序问题。
- **流程编排与交互稳定性：** 将单节点草案生成重构为 LangGraph 4 节点状态图（extract / recall / llm_draft / postprocess），以 LangGraph 作为唯一控制面，并通过 SSE 推送阶段进度、候选数量、逐天结果和最终 itinerary；典型用例首屏感知等待由约 75s 降至约 10s。
- **地图与 Provider 扩展：** 抽象 Search/Map Provider 接口，统一参数、超时、降级和调用日志，支持高德、SerpAPI、Mock 可插拔；补充坐标回填、目的地 bbox 校验和 SerpAPI 精确地点解析，海外 POI smoke 样例从 2/9 提升至 9/9 可回填。
- **编辑与版本管理：** 实现 Edit Day/slot patch 机制和 revision/diff 修订链，用户可提出“把第 2 天下安排换成东方明珠”等局部修改；系统只更新目标 Day/slot，并记录 changed_days 与改动摘要，降低“改一处影响全局”的风险。
- **一致性与质量保障：** 编辑后自动清理旧地点的坐标、图片、证据、交通、费用和风险字段，并对新地点做局部坐标/evidence 回填；建立覆盖性能、行程编辑、QA、坐标回填和海外 POI 的回归测试，关键后端回归 22 项通过。

### 技术亮点（向导师重点汇报）

**1. LangGraph 多节点架构设计**

将 140 行的单节点函数重构为 4 个独立节点 + 条件边路由。这不只是代码重构，更是释放了 LangGraph 的核心能力——节点级流式推送、条件路由、独立重试、中间状态观测。

**2. 候选排序与质量优化**

项目没有让 LLM 直接决定最终 POI，而是把 Provider 返回结果当作候选集，基于 bbox、文本匹配、alias、provider 状态、证据覆盖和预算/行程约束做 rerank/filter。后续通过 `candidate_decision_v1`、badcase report 和 manifest 观察 accepted/rejected、bbox_rejected、provider_timeout、cache_negative_hit 等问题，形成 badcase-driven ranking iteration。

**3. 性能优化的方法论**

从定位瓶颈（实测数据）→ 分析根因（单节点架构封死优化路径）→ 制定策略（重构+优化一体化）→ 实施验证（9 项回归测试）→ 识别剩余瓶颈（技术栈分析）→ 行业对标（Mindtrip 策略借鉴），形成完整的性能优化闭环。

**4. 选型决策的权衡思考**

每个技术决策都做了备选方案对比：

- 一体化重构 vs 分步重构 → 选一体化（减少无价值中间态）
- 流式渲染 vs 分步并行 → 选流式（零风险、零成本、用户感知质变）
- asyncio.gather vs 消息队列 → 选协程并行（Provider 已是 async，零部署）

**5. 关键洞察**

> "最快的 LLM 调用就是不调用 LLM"

通过候选排序和行业对标分析，认识到旅行规划 Agent 的关键不是让 LLM 一次性“想对”，而是先把工具候选筛好、排好、校验好，再让 LLM 负责组织和表达。

## 四、面试深挖问答库（新增）

> 这一部分按“更像真实面试官会问的问题”来准备。回答尽量用 STAR 结构，但不要机械背诵，建议先讲结论，再按 S/T/A/R 展开。

### 1. 你这个多步编排流程具体是怎么实现的？

**建议回答（STAR）**

- `S`：这个项目的核心问题是旅行规划链路很长，包含约束提取、工具检索、LLM 生成、校验和输出。如果全写在一个函数里，状态不透明，失败也很难定位。
- `T`：我的目标是把这条链路拆成可观测、可回退、可扩展的工作流，同时让前端能实时感知进度。
- `A`：我用 LangGraph 把流程拆成 4 个核心节点：`extract -> recall -> llm_draft -> postprocess`。`extract` 负责解析用户输入和约束检查，如果缺少 P0 字段就通过条件边直接走 early exit，不进入后续高成本节点；`recall` 负责并行调用 provider；`llm_draft` 负责流式生成；`postprocess` 负责 schema 校验、evidence 组织和最终输出。节点之间传统一份 `state`，里面带 query、constraints、recall 结果、validation、perf 等中间产物。
- `A`：前端不是等到最后一次性收结果，而是通过 SSE 接收 `stage_start`、`pipeline_complete`、`day_ready`、`final_itinerary` 这类事件，所以用户能看到“正在检索”“第 1 天已经生成”等过程状态。
- `R`：这样做以后，长任务交互稳定性明显更好，缺字段场景可以在毫秒级早退，正常场景也能渐进式反馈，用户感知比单次阻塞返回要好很多。

**追问 1：为什么一定要用 LangGraph，而不是普通函数编排？**

- 普通函数也能跑通，但有三个问题：第一，条件分支和失败回退会越来越乱；第二，中间状态难观测，排查性能瓶颈困难；第三，前端想拿到阶段性事件会比较别扭。LangGraph 对我最有价值的不是“能调用 LLM”，而是把复杂链路变成了可管理的状态机。

**追问 2：你的条件边具体怎么设计的？**

- 最关键的是把“是否继续生成”前置。比如 `extract` 节点会判断目的地、天数、预算这类硬约束是否齐全，如果不齐就直接进入 clarification/early exit 分支；如果齐了才进入 recall 和 draft。这样能避免无意义的外部调用和 LLM 消耗。

### 2. 你这个局部重规划具体怎么实现的？

**建议回答（STAR）**

- `S`：旅行规划最常见的用户行为不是“重做全部”，而是“把第 2 天换掉”“把晚上改成美食”。如果每次都全量重跑，体验差，而且会把没改的天一起改掉。
- `T`：我的目标是只修改用户指定的 Day N，尽量保持其余天不变，同时保留完整修改历史。
- `A`：我把行程设计成结构化 schema，每一天都有明确的 `day_index` 和 `slots`。编辑请求进来后，后端先定位当前 `revision`，再把“用户希望改哪一天、改什么”转成 patch 语义，对目标 Day/slot 做替换、删除或插入。
- `A`：编辑不是覆盖旧版本，而是在当前版本基础上生成新 `revision`，记录 `base_revision_id`、`change_summary` 和 `diff`。如果替换了 slot，会清理旧坐标、旧 evidence、交通、费用和风险字段，再对 changed day 缺坐标地点做局部回填。
- `R`：这套机制把“改一处影响全局”的风险降下来了，同时让历史回滚和结果对比都变得很自然。

**追问 1：怎么保证其他天不被误改？**

- 我的原则是“局部编辑只影响局部”。patch engine 只对目标 day/slot 的 payload 做替换、删除、插入，其他 day 直接继承 base revision 的内容。除非用户明确要求全局重排，否则不会整体重算。

**追问 2：如果用户连续多次编辑同一天，怎么避免版本混乱？**

- 每次编辑都以当前 revision 为 base revision 继续演化，形成 revision chain。这样历史是线性的，任何一次编辑都能回到它的父版本去看上下文。

### 3. 你的数据库表有多少张？是怎么设计的？

**建议回答（STAR）**

- `S`：这个项目不是只有聊天文本，还涉及会话、结构化行程、版本、diff、证据、当前会话态，所以数据库设计不能只放一张 message 表。
- `T`：我的目标是把“长期需要追溯的数据”和“当前运行时状态”分开设计，既支持业务查询，也支持版本管理。
- `A`：核心表我设计了 8 张主表：`users`、`conversations`、`messages`、`itineraries`、`itinerary_revisions`、`itinerary_diffs`、`itinerary_evidence`、`travel_conversation_states`。
- `A`：`users / conversations / messages` 负责传统会话链路；`itineraries` 是主行程实体，保存稳定的业务 ID、当前 revision 和顶层 trip profile；`itinerary_revisions` 存每次生成或编辑后的完整快照；`itinerary_diffs` 存改动摘要；`itinerary_evidence` 存推荐依据和来源；`travel_conversation_states` 存当前会话的 thread 级状态，比如当前 revision、当前 itinerary snapshot、聊天摘要等。
- `R`：这样设计以后，既能支持“当前版本快速读取”，也能支持“历史版本追溯”和“解释推荐依据”。

**追问 1：为什么不只用一张 itinerary 大表，把所有 JSON 都塞进去？**

- 因为那样读当前结果方便，但历史版本、diff、回滚、审计都会很别扭。我的设计是把“主实体”和“演化历史”拆开，能同时满足读性能和可追溯性。

**追问 2：为什么 `travel_conversation_states` 还要单独一张表？**

- 因为它更像 thread 级运行时视图，不完全等价于最终落库的 itinerary。它要服务多轮对话中的“当前上下文恢复”，和 revision 历史表是两个职责。

### 4. 你这个 Schema 和 `schema_version` 是怎么落地的？

**建议回答（STAR）**

- `S`：LLM 输出天然不稳定，如果没有结构约束，前后端联调会很痛苦，尤其项目在持续迭代时，新字段一加，旧前端就可能直接挂。
- `T`：我的目标是让 LLM 输出变成一个稳定契约，而不是一段“看起来像 JSON”的文本。
- `A`：我定义了 itinerary v1 schema，核心结构包括 `trip_profile`、`days`、`slots`、`budget_summary`、`evidence`、`validation` 等字段，并强制每次输出带 `schema_version`。
- `A`：版本策略上我采用的是“新增字段尽量追加，不破坏旧字段语义”。前端按版本解析，后端在 postprocess 阶段做字段补齐、默认值兜底和最小可用校验。
- `R`：这样前后端可以并行迭代，模型输出即使有漂移，也会先被后处理层校正，而不是直接冲击 UI。

**追问 1：如果未来从 v1 升到 v2，你会怎么兼容？**

- 我会保留 v1 解析路径，在后端提供兼容转换层，确保至少一个过渡周期内前端仍能消费旧结构。也就是说，升级不是“直接替换”，而是“多版本并存 + 平滑迁移”。

**追问 2：为什么不直接让前端容错解析？**

- 前端容错可以做，但那是在补救。真正稳定的做法应该是后端先把契约兜住，让前端拿到的是确定结构，不是模糊数据。

### 5. 你这个“缺字段自动追问 / 降级输出”具体怎么做的？

**建议回答（STAR）**

- `S`：旅行规划里很多输入天生不完整，比如用户只说“想去海边玩几天”，如果直接生成，结果会很玄学。
- `T`：我希望系统能区分“必须先问清楚的缺失”和“可以带假设先给草案的缺失”。
- `A`：我把约束分成 P0/P1。P0 是目的地、天数、预算这类直接影响生成路径的关键字段；P1 是出行人群、偏好、住宿风格这类会影响质量但不一定阻塞输出的字段。
- `A`：QP 处理后，如果缺 P0，就直接触发 clarification，不进入后续高成本节点；如果缺 P1，就允许先生成，但会在 `validation.assumptions` 里显式写出默认假设。
- `R`：这样既避免了“硬猜用户意图”，也避免了任何信息不全就完全不给结果，整体交互会更平衡。

**追问 1：这个分类是怎么定出来的？**

- 不是纯拍脑袋，而是从生成质量和成本角度定的。凡是会明显改变召回范围和行程骨架的字段归 P0；只影响偏好排序和文案细节的归 P1。

**追问 2：为什么不让模型自己判断要不要追问？**

- 模型可以辅助，但最终规则必须显式化，否则行为会漂。把规则前置到 QP/validation 层，系统一致性更高。

### 6. 你把地图、POI、检索这些工具能力封装成 Tool Calling，是怎么设计的？

**建议回答（STAR）**

- `S`：外部数据源有高德、SerpAPI、Mock，不同源的参数、返回结构、稳定性都不同，如果业务层直接依赖它们，后面会非常难扩展。
- `T`：我的目标是统一接入方式，让上层只关心“我要搜索什么”，不关心“具体哪个 provider 怎么调”。
- `A`：我定义了 provider 抽象层，比如 search provider、map provider，统一方法签名和返回结构。工厂层负责根据环境变量和可用性注册 provider，编排层负责并行调度、超时控制、错误收敛和降级。
- `A`：所有 provider 返回的都是统一候选对象和 error/degraded 状态，这样 ranking、filter、evidence builder 就可以复用一套逻辑。
- `R`：结果就是增加或替换数据源时，只要实现接口并注册即可，不需要侵入上层业务流程。

**追问 1：你为什么要保留 Mock provider？**

- Mock provider 主要是为开发联调和兜底场景服务。外部 API 不稳定、没 key 或超时时，Mock 能保证链路仍然可跑，这对开发效率和演示稳定性都很重要。

**追问 2：你们有没有做日志或审计？**

- 有，调用层会记录 provider 名称、耗时、错误类型和是否降级。这样线上排查时能明确知道是“模型问题”“外部 API 问题”还是“编排策略问题”。

### 7. 前端为什么能看到阶段进度和逐天渲染？这个是怎么实现的？

**建议回答（STAR）**

- `S`：旅行规划任务长，用户如果一直看到 loading，会觉得系统卡住或者失败了。
- `T`：我的目标是把长任务拆成用户可感知的过程，而不是只给最终结果。
- `A`：后端生成过程中通过 SSE 发送事件流，不同阶段发不同事件，比如开始草案、检索完成、某一天准备好了、最终 itinerary 准备好了。
- `A`：前端不是等所有天都完成，而是先接收 `day_ready` 渐进渲染部分内容，最后再用 `final_itinerary` 覆盖成完整结果。地图和时间线也都直接消费这些结构化日程数据。
- `R`：这样用户感知到的“首屏时间”会显著下降，哪怕总生成时间没那么大变化，交互体验也提升很多。

**追问 1：为什么用 SSE，不用 WebSocket？**

- 这个场景基本是单向服务端推送，SSE 更轻量，和 HTTP 体系兼容也更好，工程复杂度比 WebSocket 低。

**追问 2：逐天渲染会不会和最终结果不一致？**

- 会有这个风险，所以我把 `day_ready` 定位成渐进展示，最终还是以 `final_itinerary` 为准。也就是说，中间态是为了更快反馈，最终态才是权威结果。

### 8. 你说的 `revision / diff / request_id`，分别解决什么问题？

**建议回答（STAR）**

- `S`：做多轮编辑时，最大的风险是版本覆盖、重复提交和“改完了但不知道改了什么”。
- `T`：我希望同时解决三个问题：可追溯、可对比、可幂等。
- `A`：`revision` 解决版本快照问题，每次生成或编辑都保存完整 payload；`diff` 解决变化解释问题，记录 changed days 和 diff items；`request_id` 解决幂等问题，防止前端重试或网络抖动导致重复写入。
- `A`：这样一次编辑请求进来后，系统先看是不是重复 request，再在对应 base revision 上生成新 revision，并落一条 diff。
- `R`：结果是历史清晰、结果可回滚、接口也更稳，不容易出现重复生成或状态错乱。

**追问 1：为什么 `diff` 不在前端算？**

- 前端只能算展示层 diff，但后端才掌握完整 revision 上下文和最终权威数据，所以真正用于审计和回滚的 diff 应该由后端生成。

**追问 2：如果 request_id 命中了，你返回什么？**

- 一般直接返回之前已经生成好的结果或对应 revision，这样对调用方是透明的，幂等行为最稳定。

### 9. Redis 在你这个项目里缓存了什么？为什么这样设计？

**建议回答（STAR）**

- `S`：外部工具调用有延迟和抖动，LLM 也有成本，如果每次请求都全量重跑，体验和成本都不理想。
- `T`：我的目标是缓存“短期高复用、可容忍过期、可重算”的数据，而不是把所有东西都丢缓存。
- `A`：我主要把会话态和工具结果做短缓存，比如 recall 结果、部分会话上下文、短期语义缓存等。这些数据命中后可以直接跳过重复调用。
- `A`：但像用户、正式 itinerary 版本链、evidence 持久记录这类强一致数据仍然落 MySQL，不依赖 Redis。
- `R`：这样可以减少重复外部请求带来的抖动，同时不牺牲系统的一致性和可追溯性。

**追问 1：缓存一致性怎么保证？**

- 我不把 Redis 当真相源。真相源始终是 MySQL 和当前 revision。缓存通过 TTL 和失效策略来控制，一旦 miss 就回源重算。

**追问 2：为什么不用 Redis 存全部 itinerary？**

- 可以存热点副本，但不适合作为唯一事实来源。版本链、审计、回滚都需要持久化数据库支撑。

### 10. 你做过哪些性能优化？哪些是最有价值的？

**建议回答（STAR）**

- `S`：最开始的瓶颈是两个：一是检索串行，二是 LLM 输出阻塞，导致用户要等很久才看到内容。
- `T`：我的目标不是只看总耗时，而是同时优化“用户感知首屏”和“系统总吞吐”。
- `A`：检索侧我把 provider 调用改成并行，把原来串行的多源搜索收敛成 `asyncio.gather`；生成侧把 `ainvoke` 改成 `astream`，同时配合 SSE 做渐进式输出；流程侧增加缺字段早退，避免无效调用。
- `A`：我还补了 perf 指标采集，把 `extract_ms`、`recall_ms`、`llm_ms`、`llm_ttft_ms` 等埋到链路里，保证优化不是凭感觉。
- `R`：比较有价值的不是某一个微优化，而是“并行检索 + 流式生成 + 条件早退”组合，把等待变成了可观测且可压缩的过程。

**追问 1：你是怎么证明优化有效的？**

- 我是拿前后对比指标说话，不是只凭主观感觉。比如检索阶段和首屏感知时间都有前后基线，优化后再做回归测试，确保不是局部快了但整体变差。

**追问 2：如果让你继续优化，下一步会做什么？**

- 我会优先做“减少不必要的 LLM 调用”，比如更激进的缓存、模板复用和意图分流。因为很多时候最有效的优化不是让模型更快，而是少调一次模型。
