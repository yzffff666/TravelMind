## 一、简历描述

### 推荐版（一段式，直接粘贴）

**TravelMind — AI 旅行规划系统**

从零设计并实现的 AI 旅行规划系统，基于 LangGraph 多节点状态图引擎，支持多轮对话式行程生成与编辑。

核心工作包括：(1) 设计 4 节点 LangGraph 工作流（约束提取→并行检索→流式 LLM 生成→后处理），通过条件边实现缺字段早退（<2ms）和正常流程的智能路由；(2) 构建 QP→召回→排序→过滤→证据组织的检索流水线，Provider 层抽象多数据源（高德/SerpAPI），采用 asyncio.gather 并行化将检索耗时从 12s 降至 3s（提升 75%）；(3) 将 LLM 调用从 ainvoke 改为 astream 流式生成，配合 SSE 渐进式协议与前端逐天渲染，用户感知首屏时间从 75s 降至 10s（提升 87%）；(4) 设计 itinerary v1 结构化行程契约，支持 Edit Day N 局部重规划、revision/diff 与 patch 引擎。

技术栈：Vue 3 + TypeScript、FastAPI、LangGraph、DeepSeek LLM、Redis、MySQL

### 技术亮点（向导师重点汇报）

**1. LangGraph 多节点架构设计**

将 140 行的单节点函数重构为 4 个独立节点 + 条件边路由。这不只是代码重构，更是释放了 LangGraph 的核心能力——节点级流式推送、条件路由、独立重试、中间状态观测。

**2. 性能优化的方法论**

从定位瓶颈（实测数据）→ 分析根因（单节点架构封死优化路径）→ 制定策略（重构+优化一体化）→ 实施验证（9 项回归测试）→ 识别剩余瓶颈（技术栈分析）→ 行业对标（Mindtrip 策略借鉴），形成完整的性能优化闭环。

**3. 选型决策的权衡思考**

每个技术决策都做了备选方案对比：
- 一体化重构 vs 分步重构 → 选一体化（减少无价值中间态）
- 流式渲染 vs 分步并行 → 选流式（零风险、零成本、用户感知质变）
- asyncio.gather vs 消息队列 → 选协程并行（Provider 已是 async，零部署）

**4. 关键洞察**

> "最快的 LLM 调用就是不调用 LLM"

通过行业对标分析，认识到优化 LLM 调用速度的边际效益递减（远程 API 物理限制），真正改变格局的策略是降低 LLM 调用概率——热门模板缓存 + 多模型路由。

## 三、面试 Q&A 速查

| 问题 | 回答要点 |
|------|---------|
| 项目最大的技术挑战？ | LLM 生成耗时 65s，单节点架构封死优化路径。通过多节点重构+流式渲染，首屏提升 87% |
| 为什么用 LangGraph 而非普通函数？ | 条件边路由、节点级事件推送、独立 retry、中间状态观测——这些是普通函数做不到的 |
| 性能优化的思路？ | 先量化定位（实测基线）→ 区分"用户感知"和"实际延迟"→ 流式是零成本高收益→ 并行化是确定性收益 |
| 为什么选流式而非分步并行？ | 流式零风险不增成本，分步并行 API 成本翻倍且 rate limit 未知。远期可叠加 |
| 检索流水线怎么设计的？ | QP 提取约束 → Provider 并行召回 → 可解释排序 → 规则过滤 → Evidence Builder 组织证据链 |
| 还有什么可以优化的？ | 两个维度：LLM 维度（多模型路由 + 分步并行 + 模板缓存）和流水线维度（分层缓存短路 + 局部复用 + 异步补全） |
| 流水线智能执行是什么？ | 不每次全跑流水线——分层缓存命中跳过后续、参数微调只刷受影响阶段、重复请求自动去重 |
| 和 Mindtrip 相比差距在哪？ | 他们有本地 GPU 集群（首 token 100ms vs 我们 2-5s），我们在流式/并行/SSE 上策略一致，差距在基础设施 |
| 优化的核心洞察？ | "最快的 LLM 调用就是不调用 LLM"——通过缓存+路由使 LLM 调用概率从 100% 降至 30~50% |
